## Der Befund — gemessen in Sprint 19, nicht vermutet

Auf dem Mount ohne `unlink`-Recht (R7) hinterlässt **jeder Commit** Artefakte, die Git
selbst nicht mehr wegräumen kann: `.git/objects/**/tmp_obj_*`. Der **nächste** Git-Aufruf
im selben Repo scheitert daran.

Gemessen in diesem Lauf, dreimal in Folge:

| Aufruf | Ergebnis |
|---|---|
| `entsperre` → `setze_status(in_progress)` | ok |
| `setze_status(in_review)` **ohne** erneutes Entsperren | **Buchung gescheitert**, Wechsel zurückgenommen |
| `entsperre` → `setze_status(in_review)` | ok |
| `setze_status(done)` **ohne** erneutes Entsperren | **Buchung gescheitert**, Wechsel zurückgenommen |

> **Der Preflight räumt beim Start, und beim Start ist sauber. Was ihn stört, entsteht
> danach — und zwar durch genau die Handlung, die er ermöglichen soll.**

## ⚠ Warum das schlimmer ist als eine Unbequemlichkeit

`setze_status` (SWR-139) nimmt bei gescheiterter Buchung den Wechsel **byteweise zurück** —
das funktioniert und hat hier zweimal richtig gearbeitet. Der Schaden liegt woanders:

1. Ein Lauf, der **zwei** Statuswechsel hintereinander bucht, scheitert am zweiten,
   **egal wie sauber er gestartet ist**. Der Preflight kann das nicht abfangen: er läuft
   vorher.
2. Die Fehlermeldung nennt `unable to unlink '.git/objects/../tmp_obj_XXXX'` — sie sieht
   aus wie ein Sperrproblem eines **fremden** Prozesses und ist der Rückstand des
   **eigenen** vorigen Commits.
3. ⚠⚠ Der Rückbau ist die **richtige** Reaktion auf eine gescheiterte Buchung. Aber ein
   Lauf, der die Ausnahme nicht liest, sieht ein Ticket, das er gerade auf `done` gesetzt
   hat, wieder auf `in_review` stehen — und setzt es erneut. *Ein korrekt
   zurückgenommener Wechsel ist von einem nie versuchten nicht zu unterscheiden.*

## Was NICHT die Lösung ist

- **Eine Schleife in `verbuche`.** Sie verwandelt einen dauerhaften Fehler in eine
  Wartezeit; der Grund für „genau einmal" steht im Docstring und gilt weiter.
- **Vorsorgliches Räumen vor jedem Git-Aufruf.** Eine Sperre, die ein *laufender*
  Git-Prozess hält, beiseitezuräumen ist schlimmer, als sie stehen zu lassen.

## Drei Fragen vor dem Bauen

1. Ist `objects/**/tmp_obj_*` überhaupt eine **Sperre** — oder nur Müll, der Git beim
   nächsten Lauf zum *Warnen* bringt und den `verbuche` fälschlich als Fehlschlag liest?
   ⚠ Die Meldungen kamen als `warning:` und der Exit-Code war trotzdem ungleich 0. **Erst
   messen, welches von beidem es ist** — die Reparaturen sind verschieden.
2. Gehört das Räumen **nach** den Commit (in `verbuche`, nachdem Git fertig ist) statt
   davor? Dann ist der Zeitpunkt der, an dem sicher **kein** Git mehr läuft.
3. Ist `git gc`/`git prune` auf diesem Mount überhaupt durchführbar, oder wächst
   `.git/objects` und `verwaiste-locks` unbegrenzt? ⚠ Der Parkplatz ist bereits
   dreistellig; das ist kein Fehler, aber es ist eine Größe, die niemand misst.

## Zwischenlösung, die in Sprint 19 GEWIRKT hat

Ein Aufruf der Preflight-Räumung **vor jedem** Commit. Das ist die Umgehung und nicht die
Reparatur — sie steht hier, damit der nächste Lauf nicht dieselbe Stunde verliert, und sie
ist ausdrücklich **kein** Grund, dieses Ticket für erledigt zu halten.

### Ergebnis 2: Die Sperre ist `.git/index.lock` — und die Ursache ist eine andere

Drei Aufrufe hintereinander gegen ein stehengebliebenes `index.lock`:

| Aufruf | Exit | Meldung |
|---|---|---|
| `git add` | **128** | `fatal: Unable to create '…/.git/index.lock': File exists.` |
| `git commit` | **128** | dieselbe |
| `git rm --cached` | **128** | dieselbe |

### ⚠⚠ Ergebnis 3: Warum manche Aufrufe die Sperre hinterlassen und andere nicht

Gemessen über je einen Aufruf mit Vorab-Räumung (`index.lock` danach vorhanden?):

| Aufruf | Exit | Sperre bleibt liegen |
|---|---|---|
| `git status --porcelain` | 0 | **JA** |
| `git log`, `git diff`, `git ls-files` | 0 | nein (fassen den Index nicht an) |
| `git add` | 0 | nein |
| `git commit` | 0 | nein |
| `git reset --hard` | **128** | **JA** |

> **Umbenennen ist auf diesem Mount erlaubt, Löschen nicht. Git beendet einen
> SCHREIBENDEN Indexvorgang, indem es `index.lock` über `index` **umbenennt** — das geht
> durch. Einen bloß LESENDEN Refresh (`git status`) beendet es, indem es die Sperre
> **löscht** — und das scheitert. Der harmlose Lesevorgang hinterlässt die Sperre, an der
> der nächste Aufruf stirbt.**

⚠ Damit ist auch erklärt, warum der Befund in Sprint 19 nach **zwei** Statuswechseln
auftrat und nicht nach einem: dazwischen lag ein lesender Aufruf.

⚠ Und es erklärt, warum der Preflight das Problem nicht lösen kann: **er selbst ist ein
lesender Aufruf.** Seine letzte Handlung hinterlässt die Sperre für den, dem er den Weg
frei machen sollte.

### ⚠⚠ Der Titel dieses Tickets ist falsch, und das ist sein Ertrag

Das Ticket heißt *„tmp_obj-Reste auf einem Mount ohne unlink-Recht"*. Die Messung aus
Sprint 21 hat gezeigt, dass diese Reste **Müll** sind und keine Sperre — ein Commit lief
mit fünf `warning: unable to unlink` und **Exit 0** durch. Die Sperre, an der wirklich
etwas stirbt, ist `.git/index.lock`.

Und sie wird **nicht** vom scheiternden Aufruf hinterlassen, sondern vom **gelingenden**:

| Aufruf | Exit | Sperre bleibt liegen |
|---|---|---|
| `git status --porcelain` | 0 | **JA** |
| `git log`, `git diff`, `git ls-files` | 0 | nein |
| `git add`, `git commit` | 0 | nein |
| `git reset --hard` | 128 | **JA** |

> **Umbenennen ist auf diesem Mount erlaubt, Löschen nicht. Git beendet einen SCHREIBENDEN
> Indexvorgang, indem es `index.lock` über `index` umbenennt — das geht durch. Einen bloß
> LESENDEN Refresh beendet es, indem es die Sperre LÖSCHT — und das scheitert.**

### ⚠ Damit war Frage 2 dieses Tickets falsch gestellt — und drei Sprints lang unbemerkt

Frage 2 lautete: *„Gehört das Räumen **nach** den Commit?"* Nach dem Commit ist **nichts**
zu räumen; der Commit hinterlässt keine Sperre. Zu räumen ist nach **jedem Aufruf, der
zurückkommt** — auch und gerade nach den lesenden.

⚠ Und der Rückfall aus **SWR-134** sah drei Sprints lang wie die Lösung aus. Er ist es
nicht: er repariert den Aufruf, der **gescheitert** ist, und verlegt die Kosten damit auf
den **nächsten** Aufrufer — der eine Fehlermeldung sieht, die nach einem fremden Prozess
aussieht und der Rückstand des eigenen vorigen Laufs ist.

### Was gebaut ist

**SWR-163** — `git_schreiben._nachraeumen`: nach dem eigenen, **gelungenen** Aufruf wird
die eigene Sperre weggeräumt. Eigenes Zählfeld `nachgeraeumt` neben `geraeumt`, weil das
zwei verschiedene Fragen sind.

**SWR-164** — `preflight.parkplatz_stand`: der Parkplatz wird gemessen und gemeldet.
